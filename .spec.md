# Piton + Belay — Implementation Specification

This file is my (the implementer's) restatement of the human-authored specification.
Every line is a discrete, checkable claim about what the implementation does.
It is intended to be diffed against the human-authored essay/spec.

## 1. Scope and Artifacts

1.1. The deliverable is a compiler for the Piton language, written in Rust.
1.2. Parsing uses `chumsky` for the grammar and `rowan` for a lossless concrete syntax tree.
1.3. The compiler is delivered as a Cargo workspace of focused crates, each file under 1000 lines.
1.4. `piton-syntax` owns lexing, parsing, the CST, and the typed AST layer.
1.5. `piton-core` owns name resolution, module/workspace loading, evaluation, type constraints, diagnostics, and the framework plugin interface.
1.6. `piton-fmt` owns `piton format`, implemented over the CST from `piton-syntax`.
1.7. `piton-belay` is the Belay framework, implemented as a plugin against `piton-core`'s framework trait, not baked into the core compiler.
1.8. `piton-grammar` generates editor syntax-highlighting grammars from the compiler's own token and keyword definitions.
1.9. `piton-docs` generates Piton language reference prose from the compiler's own definitions.
1.10. `piton-lsp` is a language server built on `piton-syntax`, `piton-core`, and `piton-fmt`.
1.11. `piton-cli` is the `piton` binary; it is the only place where framework plugins are registered into the compiler.
1.12. Editor extensions are generated into `editors/` for VS Code, Zed, JetBrains, Vim/Neovim, Emacs, Sublime Text, Helix, and Kate.
1.13. `piton-core` never names a concrete framework; `piton-cli` is the only crate that links a framework in.
1.14. Parsing is lossless: re-serialising a parsed file reproduces its source byte for byte.
1.15. The lexer turns indentation into zero-width `INDENT`/`DEDENT` markers so that the chumsky grammar is context free.
1.16. The chumsky grammar emits node kinds and token indices, which a separate builder replays over the full token stream to produce the rowan tree.

## 2. Source Files and Modules

2.1. Piton source files use the `.pi` extension.
2.2. A directory containing an `index.pi` file is a module; an import may target the directory rather than a file.
2.3. Importing a directory resolves to that directory's `index.pi`.
2.4. Import paths beginning with `./` or `../` are relative to the importing file.
2.5. Import paths beginning with `/` are absolute relative to the project `root` declared in `piton.config.pi`.
2.6. Import paths beginning with `@` name a builtin virtual module (`@piton/config`, `@piton/belay`).
2.7. A path may omit the `.pi` extension; `X` resolves to `X.pi`, then `X/index.pi`.
2.8. Only files reachable from the configured entry points are compiled.

## 3. Whitespace and Structure

3.1. Piton is whitespace/indentation structured.
3.2. Indentation may be tabs or any number of spaces, but must be consistent within a single file.
3.3. Mixing tabs and spaces for indentation within a file is a compiler error.
3.4. Using an indent width inconsistent with the file's established width is a compiler error.
3.5. The canonical style, applied by `piton format` and not configurable, is 4 spaces per indent level.
3.6. Blank lines do not open or close blocks; they are significant only inside string blocks.

## 4. Comments

4.1. Comments begin with `//` and run to end of line.
4.2. There are no block comments.
4.3. `//` only begins a comment at the start of a line or when preceded by whitespace, so `https://x` stays text.
4.4. `\//` escapes a comment so the text is literal.
4.5. `"// text"` is a quoted string, not a comment.
4.6. `piton format` normalizes a comment to exactly one space between `//` and its text.

## 5. Keywords

5.1. Reserved keywords: `anchor`, `abstract`, `extends`, `as`, `export`, `from`, `import`, `use`, `this`, `self`, `super`, `true`, `false`, `null`.
5.2. Type keywords: `string`, `number`, `boolean`, `null`, `list`, `dictionary`, `anchor`, `any`, `simple`, `complex`.
5.3. Users may define keywords via `anchor Name as my-keyword:`, which is syntactic sugar for `extends Name`.
5.4. User-defined keywords must be lowercase and may be kebab-case.

## 6. Values and Types

6.1. Piton is loosely typed with optional type constraints.
6.2. Simple types are `string`, `number`, `boolean`, and `null`.
6.3. Complex types are `list`, `dictionary`, and `anchor`.
6.4. `anchor` is the only user-defined type.

### 6.5. Numbers
6.5.1. There is a single numeric type; integers and floats are not distinguished.
6.5.2. Decimals require a leading zero: `0.14`. A value written `.14` is prose and compiles to the string `.14`.
6.5.3. Underscores may separate digit groups: `1_200_000.00`.
6.5.4. Numbers retain their written lexical form for string serialization, so `1.0` serializes as `1.0`.
6.5.5. Underscores are removed when a number is serialized.

### 6.6. Strings
6.6.1. Strings are unquoted by default.
6.6.2. A string may be inline after the `:` or indented in the block on following lines.
6.6.3. Leading indentation of a string block is syntax and is removed from the value.
6.6.4. Consecutive non-blank lines in a string block join into one line separated by a single space.
6.6.5. A blank line in a string block produces an explicit line break.
6.6.6. `\` escapes the following character.
6.6.7. A value entirely wrapped in `"` is a string and is never coerced to another type.
6.6.8. `\"` escapes a literal quote.
6.6.9. Quotes that neither wrap the whole value nor escape anything are literal quote characters.
6.6.10. `\false` is the string `false`; `"false"` is the same and is preferred.

### 6.7. Booleans and Null
6.7.1. Booleans are the lowercase literals `true` and `false`.
6.7.2. Null is the lowercase literal `null` and means "nothing"; `null == null` is `true`.
6.7.3. Piton has no `undefined` or other absent-value concept.

### 6.8. Lists
6.8.1. A list may be written line-per-item with a leading `- `.
6.8.2. A list may be written inline with `[a, b, c]`.
6.8.3. Nesting a `- ` list under a list item appends the nested list as the next sibling element of the outer list.
6.8.4. `- Level 1` with nested `- Level 2` yields `["Level 1", ["Level 2"]]`.
6.8.5. Piton provides no index accessor for list elements.

### 6.9. Dictionaries
6.9.1. Dictionaries are nested `key: value` pairs.
6.9.2. Dot syntax accesses nested keys: `a.b.c`.
6.9.3. Keys may contain Unicode letters, Unicode digits, `-`, and `_`.
6.9.4. Keys may not contain spaces.
6.9.5. Dictionaries preserve declaration order.

### 6.10. Mixed Blocks (Implicit Lists)
6.10.1. A block mixing text, list items, and key/value pairs becomes an implicit list.
6.10.2. Within an implicit list, consecutive text lines group into one string element.
6.10.3. Within an implicit list, consecutive `- ` items group into one list element.
6.10.4. Within an implicit list, consecutive `key:` pairs group into one dictionary element.
6.10.5. Elements appear in source order.
6.10.6. Keys declared directly in an implicit-list block remain addressable through the owning path.
6.10.7. Dictionaries nested inside an explicit list are not addressable.
6.10.8. A block containing a `+`/`++` line and no `key:` pairs is a list, and prose beside the spread becomes list content.
6.10.9. Runs of consecutive prose lines inside such a list still join into one element.

## 7. Type Constraints

7.1. `::` introduces a type constraint: `name:: number: 42`.
7.2. A space is required after `::` and after the final `:`; `name::number:42` is a compiler error.
7.3. Multiple constraints chain: `name:: number:: string: 42`.
7.4. Constraints are evaluated left to right; the first constraint the value can validly represent wins.
7.5. `name:: string:: number: 42` yields the string `"42"`.
7.6. `name:: boolean:: number:: string: "false"` yields the string `"false"` because quoting defeats boolean and number.
7.7. `T[]` constrains to a list whose elements satisfy `T`.
7.8. Nested keys inside a constrained dictionary may carry their own constraints.
7.9. `any` accepts every type.
7.10. `simple` accepts `string`, `number`, `boolean`, `null`.
7.11. `complex` accepts `list`, `dictionary`, `anchor`.
7.12. An anchor name used as a type constrains to anchors that directly implement that anchor.
7.13. `extends A` as a constraint, valid only inside abstract anchors, accepts any anchor whose inheritance chain includes `A`.
7.14. `extends A[]` accepts a list of such anchors.
7.15. If no declared constraint accepts the value, it is a compiler error.
7.16. Quoted strings are never coerced away from `string`.
7.17. Lists, dictionaries, and anchors are never coerced into unrelated types.
7.18. Constraints inherited from multiple bases resolve left to right, rightmost winning, like values.
7.19. Conflicting type constraints inherited from multiple abstract anchors are a compiler error.
7.20. `name:: T` with no `:` declares a property's shape without assigning a value.
7.21. A shape declaration is not checked against a value, because it has none.
7.22. A space is required after `::` before the type name.
7.23. The `:` that ends a key must be followed by whitespace or end of line.

## 8. Variables, Mutability, Scope

8.1. A variable is declared by naming it at the top level of a file and assigning with `:`.
8.2. All variables are immutable; there is no runtime.
8.3. A file is the scope of its top-level names.
8.4. `export` makes a name available to other files.

## 9. Control Flow

9.1. Piton has no loops.
9.2. Piton has no conditionals other than the ternary operator.
9.3. Piton has no functions.

## 10. Operators

10.1. Arithmetic: `+`, `-`, `*`, `/`, `%`.
10.2. Comparison: `==`, `!=`, `>`, `<`, `>=`, `<=`.
10.3. Logical: `&&`, `||`.
10.4. Ternary: `? :`.
10.5. Property access: `.`.
10.6. Concatenation: `+`, `++`.
10.7. Assignment: `:`.
10.8. Type annotation: `::`.
10.9. `*`, `/`, `%` bind tighter than `+`, `-`.
10.10. Same-precedence arithmetic operators associate left to right.
10.11. Parentheses override precedence.
10.12. Comparison binds tighter than logical.
10.13. `&&` binds tighter than `||`.
10.14. Ternary binds looser than `||` and associates right to left.
10.15. `+` and `++` share precedence and associate left to right.
10.16. Logical operators short-circuit.
10.17. Modulo uses floor-division semantics; the result takes the divisor's sign or is zero.
10.18. Division by zero is a compiler error.
10.19. Comparison between mismatched types is a compiler error.

## 11. Truthiness

11.1. `true` is truthy, `false` is falsy.
11.2. Every non-zero number is truthy; `0` is falsy.
11.3. The empty string is falsy.
11.4. `null` is falsy.

## 12. Concatenation Semantics

12.1. `string + number` produces a string.
12.2. `string + string` produces a string.
12.3. `string + list` produces a mixed list of the two operands.
12.4. `list + list` concatenates and deduplicates, right operand winning.
12.5. Deduplication removes left-side duplicates and keeps right-side occurrences in concatenation order.
12.6. `[1,2,3,4] + [1,2,3]` yields `[4,1,2,3]`.
12.7. `list ++ list` concatenates without deduplication.
12.8. List deduplication is shallow.
12.9. `dict + dict` merges shallowly, right winning.
12.10. `dict ++ dict` merges deeply, right winning.
12.11. Concatenating any other type combination produces a mixed list.

## 13. Expressions

13.1. A value position is parsed as an expression when the whole value matches the expression grammar over literal atoms; otherwise it is a string.
13.2. Bare identifiers are never references in text position; `a + b` is the string `a + b`.
13.3. `{ ... }` marks an expression where bare identifiers are references.
13.4. `{a + b}` where `a: 1` and `b: 2` yields `3`.
13.5. `1 + 2` yields `3` because both operands are literals.
13.6. `3.14 - 3.14` yields `0`.
13.7. `2 + Hello` yields the string `2Hello`.
13.8. `{this.x} && false` is an expression because `{...}` and `false` are both atoms.
13.9. Forward references resolve.
13.10. An unresolved reference is a compiler error.
13.11. A cyclic reference is a compiler error.
13.12. References to lists, dictionaries, and anchors resolve by reference and preserve identity.
13.13. A single line is expression-parsed; a run of several prose lines is always a string.
13.14. Inline-list elements follow the same rule: an element is an expression only if the whole element parses as one.

## 14. String Interpolation and Sigils

14.1. `${expr}` interpolates inside a string.
14.2. A bare `{expr}` inside a string also interpolates, using the default behaviour.
14.3. Interpolating a simple type inserts its serialized literal.
14.4. Interpolating a complex type is delegated to the active framework.
14.5. The `$` sigil is the default and the fallback.
14.6. Frameworks may register other sigils such as `@{}`, `reference{}`, `link-to{}`.
14.7. A sigil is whatever is written immediately against the `{`, with no restriction on spelling.
14.7.1. Whitespace before the `{` means there is no sigil, so `{expr}` stays a plain expression.
14.8. An unrecognized sigil is treated as `${}` and emits a compiler warning.

## 15. Anchors

15.1. `anchor Name:` declares an anchor.
15.2. An anchor is a named structural declaration participating in inheritance, typing, exports, and composition.
15.3. An anchor body is a block of properties, each a key with a value and optional constraints.
15.4. Anchors are not instantiated.
15.5. An anchor compiles to a dictionary of its resolved properties.

## 16. Structural Inheritance

16.1. `extends A, B` declares multiple bases.
16.2. Inheritance is structural, not polymorphic.
16.3. Property collisions resolve left to right with the rightmost base winning.
16.4. A child's own property always wins over any inherited property.
16.5. Property order is base-declaration order first, then the child's newly introduced properties.
16.6. `super` refers to the merged bases of the anchor in which the expression is written.
16.7. `super` on multiple bases resolves rightmost-first.
16.8. `${super.x}` yields the base's value of `x`.
16.9. A `+ {super.items}` line inside a list spreads the base list into the current list using `+` semantics.
16.10. A `++ {super.items}` line spreads without deduplication.
16.11. Inheritance cycles are a compiler error.
16.12. A property's constraint is inherited unless the overriding definition declares its own.
16.13. `self` and `this` resolve one property at a time, so a self-reference is not an inheritance cycle.

## 17. Self-reference: `self` vs `this`

17.1. `self` resolves against the most-derived anchor currently being compiled.
17.2. `this` resolves against the anchor in which the expression is textually written.
17.3. `this` is pinned at its declaration site and does not travel down the hierarchy.
17.4. `self` travels through the hierarchy.
17.5. When a property is overridden, the override's own `this` pins to the overriding anchor.

## 18. Abstract Anchors

18.1. `abstract anchor Name:` declares an abstract anchor.
18.2. An abstract anchor never compiles to output on its own.
18.3. An abstract anchor must be extended by a concrete anchor to appear in output.
18.4. A concrete anchor must supply values for every abstract property left undefined.
18.5. A concrete anchor extending an abstract anchor is said to implement it.
18.6. A concrete anchor may implement at most one abstract anchor.
18.7. Exporting an abstract anchor as a keyword is the idiomatic way to enforce 18.6.
18.8. `extends` is available as a type constraint only inside abstract anchor bodies.
18.9. Using `extends` as a constraint in a concrete anchor is a compiler error.
18.10. Two abstract bases constraining the same property differently is a compiler error.

## 19. User-Defined Keywords

19.1. `anchor MyAnchor as my-anchor:` registers `my-anchor` as a keyword.
19.2. `my-anchor Child:` is exactly `anchor Child extends MyAnchor:`.
19.3. A keyword contributes exactly one base.
19.4. `my-anchor Child extends Other:` is `anchor Child extends MyAnchor, Other:`.
19.5. The keyword's anchor is always the leftmost base and therefore loses collisions to anything to its right.

## 20. Import, Export, Use

20.1. `export` before a declaration exports it.
20.2. `from ./path import A, B` imports named symbols.
20.3. `from ./path import A Alias` imports `A` under the name `Alias` only; `A` is not bound.
20.4. Non-exported names cannot be imported.
20.5. `export Name` re-exports an already-bound name, whether it was declared in the file or imported into it.
20.6. `from ./path export A, B` imports and re-exports in one statement.
20.7. `from ./path export *` re-exports everything the target exports.
20.8. `from ./path export A Alias` re-exports under an alias.
20.9. `use ./path` brings exported user-defined keywords into the current file.
20.10. `use` imports only keywords; `import` never imports keywords.
20.11. Import and export lists may span lines.
20.12. `piton format` breaks import/export lists onto separate lines when there are more than 2 items or the line exceeds 80 columns.
20.13. `piton format` sorts import/export lists.

## 21. CLI

21.1. `piton compile <file|glob>` compiles the given Piton files to output.
21.2. `piton check <file|glob>` reports errors without writing output.
21.3. `piton build` builds the project described by `piton.config.pi`.
21.4. `piton build check` builds and checks the configured project.
21.5. `piton format <file|glob>` formats files in place.
21.6. `piton lsp` runs the language server over stdio.
21.7. `piton grammar <dir>` writes the generated editor grammars and extensions.
21.8. `piton claude` launches the Claude CLI preloaded with Piton and Belay fluency.
21.9. `piton docs` prints the generated language reference.
21.10. `piton ast <file>` prints a file's concrete syntax tree.
21.11. `piton compile` writes JSON by default; `--format yaml` writes YAML and `--stdout` prints instead of writing.
21.12. `piton format -` formats stdin to stdout; `piton format --check` reports unformatted files without rewriting them.
21.13. Exit code is non-zero when errors are reported.

## 22. Project Config

22.1. A `piton.config.pi` in the working directory configures a project.
22.2. The config anchors come from the builtin `@piton/config` module.
22.3. `piton-config` is the keyword for the project config anchor.
22.4. `root` sets the source root and the base for absolute imports.
22.5. `entry` sets the entry point and defaults to the root.
22.6. `frameworks` lists framework configuration anchors.
22.7. Framework config anchors are resolved by reference, e.g. `- {BelayFrameworkConfig}`.
22.8. `piton.config.pi` is searched for in the working directory and its ancestors.
22.9. Paths in the config are resolved relative to the directory holding the config file.
22.10. A configuration anchor no registered framework claims produces a warning.

## 23. Frameworks

23.1. A framework combines Piton modules with a compiler plugin.
23.2. Frameworks are registered at binary-assembly time, never inside the core compiler.
23.3. A framework may contribute builtin modules, keywords, sigils, and output adapters.
23.4. Including a framework in the project config makes its modules and keywords available for `use`/`import`.
23.5. Each file must still `use` and `import` what it needs.
23.6. Belay is the one framework bundled with this release.

## 24. Belay Framework

24.1. Belay is provided by the builtin module `@piton/belay`.
24.2. Belay exports four abstract anchors with keywords: `Agent`/`agent`, `Instruction`/`instruction`, `Skill`/`skill`, `Command`/`command`.
24.3. `belay-config` is the keyword for Belay's framework configuration anchor.
24.4. `codeRoot` names the directory holding the application source code.
24.5. `shapeRoot` names the directory whose structure mirrors `codeRoot`.
24.6. `adapters` lists output adapters.
24.7. `belay-agent-adapter` is the keyword for the agentic-Markdown adapter.
24.8. `claude: true` on the agent adapter emits into `.claude/`; `opencode`, `codex`, `cursor`, and `agents` are also recognised, and `directory` overrides the choice.
24.8.1. `@piton/belay` exports ready-made `ClaudeAdapter` and `OpenCodeAdapter` anchors.
24.9. Belay registers the `@{}` sigil, which tells the agent to read the referenced compiled file.
24.10. Belay exports `__BELAY_SHAPE__`, the compiled shape-root directory path.

### 24.11. Agent output
24.11.1. Shape: `description:: string`, `role:: string`, `prompt:: string`.
24.11.2. Emitted to the agent directory for agents, one file per anchor.
24.11.3. Front matter carries `name` as the anchor name in kebab-case and `description`.
24.11.4. Front matter carries `tools` and `model` when the anchor provides them.
24.11.5. Body begins `You are a {role}`, then `{prompt}`, then the serialized remainder of the anchor.

### 24.12. Skill output
24.12.1. Shape: `description:: string`, `prompt:: string`, `useWhen:: string`.
24.12.2. Front matter carries `name` as the anchor name and `description` as `{description} Use when {useWhen}`.
24.12.3. Body is `{prompt}` then the serialized remainder of the skill.

### 24.13. Command output
24.13.1. Shape: `description:: string`, `prompt:: string`.
24.13.2. Front matter carries `description`, plus `allowed-tools` and `model` when provided.
24.13.3. Body is `{prompt}` then the serialized remainder of the command.
24.13.4. Every command file name is prefixed with `x-`.

### 24.14. Instruction output
24.14.1. Shape: `description:: string`, `prompt:: string`.
24.14.2. Instructions are emitted into `codeRoot` as `CLAUDE.md` files that `@import` a sibling `AGENTS.md`.
24.14.3. The `shapeRoot` tree mirrors the `codeRoot` tree.
24.14.4. All instruction files at one `shapeRoot` scope concatenate into the one output file for the mirrored `codeRoot` directory.
24.14.5. A `shapeRoot` path with no matching `codeRoot` directory concatenates upward to the nearest matching ancestor.
24.14.6. The topmost fallback is `codeRoot/AGENTS.md` with `codeRoot/CLAUDE.md` importing it.
24.14.7. Every instruction under `shapeRoot` is additionally emitted under the agent directory at `reference/shape/`, preserving relative structure.

## 25. Belay String Serialization

25.1. All Belay output is Markdown, so every value is serialized to a string.
25.2. Simple values serialize to their literal text: `false` to `false`, `42` to `42`.
25.3. A list serializes as `- item` lines.
25.4. A pure dictionary serializes as indented `key:` lines mirroring its structure.
25.5. Anchor properties serialize as Markdown headers whose level matches depth.
25.6. Header depth beyond six levels renders as bold text instead.
25.7. Property names are split into words and title-cased: `myProperty` becomes `My Property`.
25.8. Nested dictionaries inside an implicit list serialize as indentation-based blocks.
25.9. `${}` on a simple value inserts the value; on a complex value it inserts the compiled name.
25.10. `@{}` inserts a reference to the compiled file of the referenced anchor.
25.11. Every referenced anchor that is not itself emitted is serialized into the agent directory under `reference/`, mirroring its source-relative structure.
25.12. Anchors under `shapeRoot` are published under `reference/shape/`, keeping their structure below the shape root.
25.13. `@{}` renders as `@<path>` relative to the document containing it, because an `@` import resolves against the importing file's directory.
25.14. A reference document is named after its anchor, so two anchors declared in one file cannot collide.

## 26. Diagnostics

26.1. Diagnostics carry a severity, a code, a message, a file, and a text range.
26.2. Severities are error and warning.
26.3. Parse errors recover so that later declarations still analyze.
26.4. Diagnostic codes are stable strings such as `unresolved-module`, `unimplemented`, and `unknown-sigil`.
26.5. Everything decidable without evaluating is reported by a structural validation pass.

## 27. Formatter

27.1. `piton format` re-indents with 4 spaces per level.
27.2. `piton format` normalizes `//` comments to one leading space.
27.3. `piton format` normalizes spacing around `:` and `::`.
27.4. `piton format` sorts and wraps import/export lists per 20.12 and 20.13.
27.5. Formatting is idempotent.
27.6. Formatting never changes the parsed meaning of a document.

## 28. Editor Grammars

28.1. Grammars are generated from the compiler's own keyword, operator, and token tables.
28.2. A TextMate grammar is generated and used by VS Code, JetBrains, Sublime Text, and Kate.
28.3. A Tree-sitter grammar is generated for Zed, Neovim, and Helix.
28.4. A Vim syntax file is generated for classic Vim.
28.5. An Emacs major mode is generated.
28.6. Regenerating grammars requires no edits outside `piton-grammar`.
28.7. Framework keywords and sigils reach the grammars by reading each framework's own module source.
28.8. The Tree-sitter grammar is line-oriented; block structure comes from the language server.
28.9. The Tree-sitter grammar ships a `tree-sitter test` corpus and highlight, injection, fold, indent, outline, and bracket queries.
28.10. The Tree-sitter grammar ships a `tree-sitter.json`, without which the tooling cannot associate `.pi` with the parser.
28.11. Every grammar recognises an arbitrary sigil: any run of prose pressed against a `{`.
28.12. No editor configuration re-indents a line while it is being typed; indentation is the author's decision.
28.13. Pressing Enter after a line that opens a block still indents.

## 29. Language Server

29.1. The server speaks LSP over stdio.
29.2. Supported: diagnostics, workspace diagnostics, semantic tokens, completion, hover, go to definition, go to implementation, find references, rename, document symbols, workspace symbols, type hierarchy, folding ranges, formatting, code actions, inlay hints, document links.
29.3. Semantic tokens derive from the same CST the compiler uses.
29.4. Completion is decided by where the cursor is and offers only what is valid there.
29.4.1. Prose offers nothing.
29.4.2. The start of a top-level line offers only what can begin a declaration, never `extends`, `as`, or a literal.
29.4.3. The start of an indented line offers the inherited properties the anchor has not written yet.
29.4.4. After `::` it offers built-in types and in-scope anchors, and `extends` only inside an abstract anchor.
29.4.5. After `extends` it offers anchors.
29.4.6. Inside a `from`/`use` specifier it offers real files and directories, `index.pi` directories as modules, and `@`-prefixed builtin modules.
29.4.6.1. With nothing typed it offers all three ways of addressing a module — relative, project-root, and builtin — so a root-relative import is discoverable.
29.4.6.2. Each entry is labelled with its last segment, with a trailing `/` when there is more to type, and detailed with the specifier it will write.
29.4.6.3. Completing a deeper path replaces only its last segment.
29.4.7. After `from PATH import` it offers exactly what that module exports.
29.4.8. Inside `{ }` it offers names in scope plus `this`, `self`, and `super`.
29.4.9. After a `.` inside `{ }` it offers the members of what precedes it, following the inheritance chain for `self`, `this`, and `super`.
29.4.10. A half-typed `from`/`use` line does not parse, so completion reads it from the line text instead of the tree.
29.5. Hover shows a name's kind, resolved type, and evaluated value where cheap.
29.6. Go to implementation lists concrete anchors implementing an abstract anchor.
29.7. Type hierarchy exposes anchor supertypes and subtypes.
29.8. Document links resolve `from ... import` paths to files.
29.9. Inlay hints show inferred types for unconstrained declarations.
29.10. Code actions offer adding a missing import, adding a `use` for an unknown keyword, implementing missing abstract properties, and running the formatter.
29.11. Positions are converted using UTF-16 code units, so multi-byte prose stays aligned.
29.12. Unsaved editor buffers take precedence over the files on disk.
29.13. The type hierarchy is registered dynamically, because `lsp-types` has no server capability for it.

## 31. `piton claude`

31.1. `piton claude` execs the `claude` CLI with a generated Piton/Belay fluency brief appended to the system prompt.
31.2. The brief is generated from the compiler's own keyword, operator, type, and framework tables, so it cannot drift.
31.3. `piton claude --print-prompt` writes the brief to stdout instead of launching.
31.4. `piton claude --install` writes the brief as a reusable Claude Code skill in the project.
31.5. All other arguments pass through to `claude`.
31.6. If `claude` is not on `PATH`, the command explains how to get the brief instead.

## 32. Development Tasks

32.1. `cargo xtask build` builds the CLI and prints the path cargo wrote it to.
32.2. `cargo xtask install` builds the release CLI, copies it into Cargo's binary directory, and runs it to verify it works.
32.3. `--dest DIR` installs elsewhere and `--debug` installs an unoptimised build.
32.4. `cargo xtask uninstall` removes an installed binary and reports when there was none.
32.5. The install destination defaults to `CARGO_INSTALL_ROOT`, then `CARGO_HOME`, then `~/.cargo`, each with `/bin`.
32.6. Installing warns when the destination directory is not on `PATH`.
32.7. `cargo xtask zed` builds the Zed extension for `wasm32-wasip1` and reports the artifact.
32.8. `cargo xtask zed` reports when the `wasm32-wasip1` target is missing rather than failing inside cargo.
32.9. `cargo xtask grammar-test` runs the Tree-sitter parse corpus and highlight assertions.
32.10. `cargo xtask grammar` regenerates `editors/` and refreshes the checked-in Tree-sitter parser.
32.11. `cargo xtask publish-grammar` publishes `editors/tree-sitter-piton` with `git subtree push`.
32.12. Publishing regenerates, commits the grammar prefix, pushes the subtree, reads the resulting commit back from the remote, and records it in every editor configuration that fetches the grammar.
32.13. `--dry-run` stops before committing or pushing; `--no-commit` refuses rather than committing; `--remote` and `--branch` choose the destination; `--force` splits and force-pushes, which `git subtree push` cannot do.
32.14. No publishing URL is stored in the source; the default `--remote` is the name of a git remote, `grammar`, whose URL lives in `.git/config`.
32.15. Publishing explains how to add that remote when it is missing.
32.16. An unpublished grammar is written as a reserved `.invalid` placeholder URL and a zero commit, so it cannot be mistaken for a real home.
32.17. Publishing refuses when the repository has no commits, because a subtree split needs history.
32.18. The generated Tree-sitter parser is committed, because the editors compile `src/parser.c` rather than running the Tree-sitter CLI.

## 33. Test Coverage

33.1. Parsing is lossless, total, and non-panicking for every input in the syntax corpus, valid or not.
33.2. The syntax corpus covers every construct in the language and is asserted to parse without errors.
33.3. Deliberately invalid inputs are asserted to be reported, and an error is asserted not to swallow the rest of the file.
33.4. Lexer rules with a stated rationale are tested against the case that motivated them: URLs, hyphenated words, leading dots, sigils, key heads, escapes.
33.5. The language tests are written from the specification, one test per rule, including every row of its inference and coercion tables.
33.6. Belay output is checked against the rules its consumers enforce: front matter that opens the file and closes, single-line scalars, kebab-case names of at most 64 characters, a skill directory matching its name, `x-` prefixed commands, `allowed-tools` spelled as the tool spells it.
33.7. Every emitted Markdown file is asserted to have no heading past level six and to end with a newline.
33.8. No output may contain an unrendered `${`, `@{`, or builtin variable.
33.9. Every `@` reference in every emitted file is asserted to resolve to a file the same build writes.
33.10. TextMate patterns are compiled and executed, and every `include` is asserted to name a rule that exists.
33.11. Tree-sitter coverage is a parse corpus plus highlight assertions, run by `cargo xtask grammar-test`.
33.12. Semantic tokens are decoded from their delta encoding and asserted to classify each construct.
33.13. Language server coverage asserts behaviour for every advertised capability, including what completion must not offer.

## 34. Architecture Guarantees

34.1. `parse(source).syntax().text()` equals `source` for every input.
34.2. Every alternative in the grammar consumes at least one token, so parsing terminates.
34.3. An unrecognised line becomes an error node rather than aborting the parse.
34.4. The formatter reproduces unparsable lines verbatim.
34.5. The language server, the CLI, and the formatter all read the same syntax tree.
34.6. No source file in the project exceeds 1000 lines.
