# Decisions

Choices I made where the human-authored specification left room. Each entry
says what was ambiguous, what I picked, and why.

# Project Layout

- The compiler is a Cargo workspace rather than one crate, so the framework
  plugin boundary is enforced by the compiler itself: `piton-core` cannot name
  `piton-belay`, only `piton-cli` links them together.
- Crates: `piton-syntax` (lexer, grammar, CST, AST), `piton-core` (resolution,
  evaluation, framework interface), `piton-fmt`, `piton-belay`, `piton-grammar`,
  `piton-docs`, `piton-lsp`, `piton-cli`.
- Editor integrations live in `editors/` and are generated by `piton grammar`
  from `piton-grammar`, which reads the compiler's own kind tables. They are
  checked in so a user can install them without building anything.
- Every file is kept under 1000 lines; large modules are split by concern
  (`lexer/mod.rs` + `lexer/value.rs`, `parser/mod.rs` + `parser/expr.rs` +
  `parser/tree.rs`).

# Dependencies

- `chumsky` 0.13 for the grammar and `rowan` 0.17 for the tree, as requested.
- `indexmap` for dictionaries, because Piton dictionaries must keep declaration
  order and the order shows up in every output format.
- `serde_json` for JSON output. YAML is emitted by a small hand-written writer
  rather than a dependency, since `serde_yaml` is unmaintained and Piton only
  ever writes YAML, never reads it.
- `tower-lsp` for the language server, `clap` for the CLI, `globset`/`walkdir`
  for file selection.
- No dependency reads Piton source except `piton-syntax`.

# Lexing and Parsing Architecture

- The lexer is hand-written and line-oriented; chumsky parses the resulting
  token stream. A whitespace-sensitive language is only context free once
  indentation has become `INDENT`/`DEDENT` markers, and doing that in the lexer
  keeps the chumsky grammar readable.
- `INDENT`/`DEDENT` are zero-width tokens that the tree builder drops, so the
  rowan tree stays byte-for-byte lossless.
- The chumsky grammar produces a lightweight index-based tree that is replayed
  over the full token stream to build the rowan green node. This keeps the
  grammar free of tree-building side effects and keeps trivia handling in one
  place.
- Parse errors are recovered by an explicit "error line" alternative rather than
  chumsky's recovery combinators, so parsing always yields a complete tree and
  diagnostics can be phrased with more context during validation.

# Lexical Decisions

- `//` only starts a comment at the start of a line or after whitespace. The
  spec requires escaping `//` inside prose, but without this rule every URL in a
  document would need escaping, which would make the language unpleasant for its
  actual purpose.
- In prose, an operator is only an operator when it stands alone between spaces.
  `well-known` is one word, `3.14 - 3.14` is arithmetic. Without this rule every
  hyphenated word and sentence dash would be tokenised as a subtraction.
- `.` is never an operator in prose, only inside `{ }`. Sentences end in periods.
- A `-` continues an identifier only when it sits directly between two
  identifier characters, so `my-key` is one name while `a - b` is subtraction.
- A run of prose immediately followed by `{` is a sigil when it reads as `$`,
  `@`, or a lowercase kebab-case word. This is how `${`, `@{`, and
  `reference{` are all recognised by one rule.
- Comment-only lines are treated as trivia in their entirety, including their
  newline, so a comment inside a string block does not introduce a line break.
- Numbers keep their written spelling (minus `_` separators) so that
  `version: 1.0` interpolates as `1.0` rather than `1`.

# Value and Expression Semantics

- A value region is an expression exactly when the whole region parses as one
  over literal atoms; otherwise it is prose. This is the rule that makes
  `1 + 2` evaluate to `3` while `a + b` stays the string `a + b`, and it is
  applied uniformly to inline values, block lines, and inline-list elements.
- A single line inside a block is expression-parsed; a multi-line run is always
  prose. Two adjacent prose lines that happen to look like arithmetic should not
  silently become a number.
- Strings never coerce to `boolean` or `number`. The specification reaches the
  same result through quoting, but stating it as a rule also gives `\false` the
  string behaviour the spec asks for.
- Simple values (`number`, `boolean`, `null`) do coerce to `string`, because
  `x:: string:: number: 42` is specified to be `"42"`.
- `+` on two numbers is arithmetic addition, not textual concatenation.
- Interpolating a complex value with `${}` yields the value itself when no
  framework claims the sigil, which is what makes the specification's JSON
  example produce a mixed list.
- Adjacent text parts merge into one string; when a complex value splits them,
  the surrounding whitespace is trimmed, matching the specification's
  `["Information about Piton", { ... }]`.

# Blocks and Lists

- A block that mixes prose, list items, and properties becomes an implicit list
  whose runs of like-shaped lines are grouped, in source order.
- A list item that has both a value and a nested block contributes two elements:
  its own value, then the nested list. This is what makes `- Level 1` with a
  nested `- Level 2` produce `["Level 1", ["Level 2"]]`.
- The specification's `nestedLists` example shows one extra level of array
  nesting around the inline `[And, With, Bracket, Syntax]` list than its own
  `nestedMarkdownList` rule produces. I implemented the rule, not the example,
  so the inline list appears once.
- A block containing a `+`/`++` line and no properties is a list block: prose
  beside the spread becomes list content rather than turning the block into an
  implicit list. Runs of consecutive prose lines still join into one element.
- Spreading a non-list value appends it as a single element rather than
  erroring, so `+ {super.description}` on a string behaves sensibly.

# Anchors and Inheritance

- Properties are resolved lazily, one at a time. `self.name` inside an anchor
  looks up a single property instead of compiling the whole anchor, which is
  what stops self-reference from being an inheritance cycle.
- `this.x` resolves `x` in the pinned anchor's chain; within that evaluation
  `this` re-pins to whichever anchor defined `x`, while `self` keeps pointing at
  the most-derived anchor.
- A type constraint is inherited unless the overriding definition declares its
  own. A child that re-states a value without a `::` keeps the abstract's
  constraint, which is the only reading under which abstract shapes are enforced.
- Property order in a compiled anchor is base-declaration order first, then the
  properties the child introduces.
- A bare `super`, `this`, or `self` used without a property yields a dictionary
  of the corresponding properties.
- An anchor whose body is a mixed block still exposes the properties written in
  its dictionary runs.
- A property written as `name:: type` with no `:` is a shape declaration, not an
  assignment. It evaluates to `null` and its constraint is not checked against
  that null, because there is no value to check. In an abstract anchor the same
  syntax means "an implementer must supply this", which is where the
  specification uses it.
- Two abstract bases that constrain the same property differently are a compiler
  error, as the specification requires; the comparison is on the rendered
  constraint chain.

# Modules

- A module specifier resolves in this order: `X.pi`, then `X/index.pi`. A
  specifier that already ends in `.pi` is used as written.
- `@`-prefixed specifiers are builtin modules contributed by the compiler or by
  a framework; they cannot themselves use relative imports.
- `use` collects keywords from a module's exported anchors, including anchors it
  re-exported, so `use ./dir` works through an `index.pi`.
- Import cycles are tolerated for exports (guarded against infinite recursion);
  value cycles are still errors.

# Diagnostics

- Diagnostics carry a stable machine-readable code (`unresolved-module`,
  `unimplemented`, `unknown-sigil`, ...) so editors and CI can filter them.
- An unknown interpolation sigil is a warning and falls back to `${}`, as
  specified.
- Everything decidable without values is reported by a structural validation
  pass, so evaluation only reports what it uniquely knows.
- A value that fails every constraint keeps its original value in the output so
  that one bad property does not cascade into unrelated errors.

# Configuration

- `piton.config.pi` is searched for in the working directory and its ancestors.
- `@piton/config` declares `PitonConfig as piton-config` with only `root`
  required. Making `entry` or `frameworks` required abstract properties would
  break configurations the specification shows as valid.
- `entry` defaults to `root`.
- Framework configuration anchors are claimed by asking each registered
  framework whether a given configuration value is its own, so the core never
  names a framework.

# Belay Output Layout

- Agents become `<agent-dir>/agents/<kebab-name>.md`, skills become
  `<agent-dir>/skills/<kebab-name>/SKILL.md`, and commands become
  `<agent-dir>/commands/x-<kebab-name>.md`. The skill directory shape is what
  Claude Code and OpenCode expect.
- The specification writes a skill's front-matter `name` as "the anchor name".
  I kebab-case it, as agents already are. The tools that read these files
  require lowercase kebab-case names, and a literal anchor name would produce a
  file they reject.
- The specification mentions both a `reference/shape` directory and a
  `references/` directory. I use one directory, `reference/`, with shape
  documents under `reference/shape/`. Two directories differing by one letter in
  the same output tree would be a trap for the agents reading them.
- `@{X}` renders as `@<path>`, the marker agentic tools already understand as
  "read this file". The path is relative to the document that contains it, not
  to the project root: Claude Code resolves an `@` import against the importing
  file's directory, which I confirmed empirically — an `@alpha.md` written in
  `sub/inner.md` loads `sub/alpha.md`. Because the same text can land in several
  documents at different depths, the path is rewritten per output file at emit
  time, once it is known where the text ended up.
- A reference document is named after its anchor rather than its source file, so
  two anchors declared in one file cannot overwrite each other and `@{Name}`
  always points at `Name.md`. The directory structure still mirrors the source.
- `${X}` on a complex value renders as the anchor's name, per the specification's
  "the compiled name".
- The agent adapter recognises `claude`, `opencode`, `codex`, `cursor`, and
  `agents` flags, plus an explicit `directory`. The specification only names
  `claude`; the rest follow the same shape and cost nothing.
- `@piton/belay` exports ready-made `ClaudeAdapter` and `OpenCodeAdapter`
  anchors so that both spellings in the specification's examples work: importing
  an adapter, and declaring one with `belay-agent-adapter`.
- An instruction's own name becomes its level-one heading, so the rest of its
  properties serialize from level two.
- `belay-config` requires only `codeRoot`. Making `shapeRoot` or `adapters`
  required abstract properties would reject configurations the specification
  shows.

# Editor Grammars

- The Tree-sitter grammar is line-oriented rather than indentation-structured.
  Tracking `INDENT`/`DEDENT` needs an external C scanner, and every consumer of
  the grammar wants it for highlighting, folding, and indent heuristics, which
  work per line. Structure comes from the language server, which uses the real
  compiler grammar.
- In that grammar, names, declaration keywords, and prose share one `word`
  token. A Piton line is ambiguous until its end — `shape Concrete:` is a
  declaration and `shape concrete text` is prose — and giving each role its own
  token would force the decision on the lexer, which cannot see far enough. One
  token turns the ambiguity into a parse conflict, which the GLR parser
  resolves.
- A property key token includes its trailing colon, because the colon is the
  only thing that distinguishes a key from a word.
- A URL is its own token so that the `//` inside it is never lexed as a comment,
  which is the same outcome the compiler's word-boundary rule produces.
- The Zed and Helix integrations point at a Tree-sitter grammar repository that
  the user must publish or redirect to a local path; neither editor can consume
  a grammar that only exists inside this repository.
- The JetBrains plugin ships both a TextMate bundle, which works in the free
  IDEs, and an LSP descriptor, which only the paid IDEs can run.

# CLI

- `piton compile` writes JSON next to each input by default; `--format`
  selects `json` or `yaml`, and `--stdout` prints instead.
- `piton build check` is spelled as a subcommand of `build`, matching the
  specification's table.
- `piton compile` on several files produces one document per file, keyed by the
  file's top-level names, because a Piton file has no single root value.
- A project whose entry is a directory with no `index.pi` treats every `.pi`
  file under it as a root.
- `piton claude` was requested after the specification: it execs the `claude`
  CLI with a generated Piton/Belay fluency brief appended to the system prompt.
  The brief is generated from the compiler's own tables and from each
  framework's own module source, so it cannot drift. `--print-prompt` dumps it
  and `--install` writes it as a Claude Code skill.
- `piton docs` and `piton ast` are additions: the first prints the generated
  reference, the second prints a parse tree, which is the only practical way to
  debug a whitespace-sensitive grammar.

# Development Tasks

- Installing the CLI is a checked-in `cargo xtask install` rather than a
  copy-paste recipe, so the command that produces an installed `piton` is
  versioned with the code that it installs.
- `xtask` is an ordinary workspace member rather than a nested workspace, so
  `cargo clippy --all-targets` and `cargo test` cover it like everything else.
  It costs one small crate on a plain `cargo build`.
- The task locates the built binary from cargo's own JSON build messages rather
  than guessing at `target/<profile>/piton`, so a custom `CARGO_TARGET_DIR` or a
  cross-compilation target still resolves correctly.
- It invokes the `cargo` that invoked it, via `$CARGO`, so the task cannot build
  with a different toolchain than the one the user selected.
- The default destination follows `cargo install`: `CARGO_INSTALL_ROOT`, then
  `CARGO_HOME`, then `~/.cargo`. Rust users already have that directory on
  their `PATH`.
- Install unlinks the old binary before copying rather than writing over it, so
  a copy that is already running keeps working.
- After installing, the task runs `piton --version`, so a binary that cannot
  start is reported at install time rather than the next time it is used.

# Zed Extension

- The Zed extension is a WebAssembly component, because Zed has no declarative
  way to start a language server: `[language_servers]` in `extension.toml` only
  registers a name, and the command comes from the extension's
  `language_server_command`.
- The extension downloads nothing. `piton lsp` is the binary the user already
  builds, so the extension only locates it: an explicit `lsp.piton.binary.path`
  setting first, then `$PATH`, and a message pointing at `cargo xtask install`
  if neither works.
- `editors/zed/Cargo.toml` declares an empty `[workspace]` so the crate is its
  own workspace. It is built for `wasm32-wasip1` by Zed, not by the Piton
  workspace it happens to live inside.
- `[grammars.piton]` ships a placeholder commit SHA rather than a branch name.
  Zed fetches grammars over git and requires a full SHA; there is no way to
  point it at a directory in this repository, so publishing
  `editors/tree-sitter-piton` is a step the user has to take.
- `cargo xtask zed` builds the extension the way Zed will, so a broken extension
  surfaces at the command line instead of inside the editor.

# Publishing the Grammar

- `editors/tree-sitter-piton` is published to its own repository as a
  `git subtree` of this one, so this repository stays the single source of
  truth and the published history stays a faithful projection of it.
- The generated parser (`src/parser.c` and its headers) is committed rather than
  ignored. Zed and Helix compile it directly; neither runs `tree-sitter
  generate`, so a published grammar without it cannot be built.
- The publish uses `git subtree push`, not a hand-rolled split and push, so the
  behaviour is git's own. The commit to pin then comes from `git ls-remote`:
  asking the remote what it has is more truthful than trusting a local split.
  `--force` is the one exception — `git subtree push` cannot force, so that path
  splits and pushes by hand, for when history here has been rewritten.
- `cargo xtask publish-grammar` regenerates before pushing, because the
  published README names the remote and is itself inside the prefix.
- It commits the grammar prefix on your behalf when it is dirty, because
  `git subtree split` only sees committed history. `--no-commit` makes it refuse
  instead, and `--dry-run` stops before committing or pushing.
- After pushing, it re-runs the generator with the new commit so the Zed, Helix,
  and Neovim configurations pin exactly what was pushed, and commits that pin
  separately from the grammar itself.
- `piton grammar` carries an existing pin forward unless `--grammar-repo` or
  `--grammar-rev` is passed, so regenerating after an unrelated language change
  cannot silently unpin the editors. An unpinned placeholder carries nothing and
  is replaced by the default.
- No publishing URL is stored in the source. What is fixed is the *name* of a
  git remote, `grammar`; its URL lives in `.git/config`, where remotes belong,
  so each clone can publish somewhere else without editing any file. `--remote`
  takes either a remote name or a URL for a one-off.
- Until the grammar has been published, the generated files carry
  `https://example.invalid/tree-sitter-piton.git` and a zero SHA. `.invalid` is
  a reserved TLD, so nothing can mistake the placeholder for a real home, and
  the Zed manifest says so in a comment with the two commands that fix it.
- The workspace excludes `editors/`, because the generated integrations contain
  their own crates — the Zed extension is built for `wasm32-wasip1` by Zed, not
  by this workspace.

# Testing

- "Correct" for Belay output means what the tools that read it enforce, not what
  the specification says in prose: front matter that opens the file and closes,
  scalars that stay on one line, kebab-case names of at most 64 characters, a
  skill directory that matches its `name`, and `allowed-tools` spelled the way
  Claude Code spells it. Those rules are applied to every emitted file rather
  than to one example.
- "Correct" for highlighting means the patterns actually run. The TextMate
  grammar is a pile of regular expressions, so the tests compile every one of
  them and execute the interesting ones against lines from the specification —
  a URL that must not become a comment, a hyphenated word that must not become
  a subtraction. I checked the tests bite by breaking those two patterns and
  watching them fail.
- Tree-sitter is tested by `tree-sitter test`, which needs the grammar to be
  discoverable, which needs a `tree-sitter.json`. Adding one is why highlight
  assertions run at all; `cargo xtask grammar-test` writes the throwaway CLI
  config so nobody has to edit `~/.config/tree-sitter`.
- Semantic tokens are decoded back out of their delta encoding before being
  asserted on. Counting tokens proves nothing; naming the type of each one is
  the actual contract with the editor.
- The syntax tests assert three invariants over a corpus — lossless, total,
  non-panicking — rather than one test per snippet, so adding a construct to the
  corpus extends every invariant at once.
- Completion tests assert what is *not* offered as much as what is. The
  regression that mattered was noise, and noise is invisible to a test that only
  checks for presence.

# Language Server

- Completion is decided by *where* the cursor is rather than by matching the
  line against patterns, and each place offers only what is valid there. The
  earlier version offered every reserved word at the start of every line,
  including `extends` and `as`, which are never valid there, and offered
  `true`/`false`/`null` where a property key belongs.
- Prose offers nothing at all. Most of a Piton file is prose, and a completion
  popup over a sentence is noise.
- Member completion after `.` replaced the old `self.<every property>` entries:
  one entry per property multiplied by every name in scope was the single
  largest source of noise, and `.` is where that information belongs.
- `self`, `this`, and `super` complete from the inheritance chain rather than
  from a compiled value, so they work before the file compiles.
- Path resolution lives in `Db`, next to the resolver the compiler uses, so the
  language server cannot develop its own idea of what a specifier means.
  `Db::lookup_module` answers without loading, for tools that only want to know
  what a path points at.
- A half-typed `from`/`use` line does not parse into a declaration, which is
  exactly when completion runs, so those lines are read from the line text. The
  tree still decides everywhere else.
- On the first line of an empty anchor body there is no block node yet, so the
  enclosing anchor is found by looking back to the nearest declaration that only
  whitespace separates from the cursor.
- The server re-analyses the project on every change rather than being
  incremental. Piton projects are documents, and a full rebuild guarantees the
  editor and the compiler never disagree.
- An offset between two tokens resolves to the token on its right, which is the
  one the cursor sits in front of.
- Completion is driven by what the line looks like to the left of the cursor,
  because Piton has few places a name can appear.
- Inlay hints show the inferred type only where no constraint was written.
- The type hierarchy is registered dynamically at `initialized`, because
  `lsp-types` 0.94 has no `typeHierarchyProvider` server capability.
